# 长截图（滚动截图）：开源参考 + 咔嚓现状实测与优化清单

调研与实测日期：2026-09-30。文中的 star / 许可证 / 提交时间均通过 GitHub API 或源码原文核实；标 **未核实** 的请勿当事实使用。
实测环境：Apple Silicon，Swift 6.4 release 构建；合成"网页"内容，帧尺寸 1600×1200 与 2560×1600。

---

## 一、结论先说

1. **有开源参考，而且 macOS 上就有两个能直接读源码的同类项目**：`Brkgng/ScrollSnap`（MIT，Swift，929★）和 `sw33tLie/macshot`（GPL-3.0，Swift，3634★，唯一把"自动滚动"做完整的 macOS 开源实现）。前者可放心借鉴代码，后者许可证是 GPL-3.0，**只能读思路、不要复制代码**。
2. **不要盲目照抄"Vision 配准"这条路**。我拿咔嚓现有的 MAD 搜索和 ScrollSnap 的 Vision 路线在同内容上对拍，结果是：**没有固定元素时两边都对；一旦出现固定顶栏/底栏，Vision 全帧配准会直接"锁死"在静止的 chrome 上返回 0 位移**（3/8 命中），而 ScrollSnap 的 5 条带共识在"顶栏+底栏"同时存在时也拿不到 4/5 共识（0/8）。
3. **咔嚓现在最严重的不是性能，是"固定底栏被当成内容重复贴进长图"**：`ScrollingStitcher` 只处理顶部 frozen header，没有底部固定区概念，而追加的内容永远取"新帧最底部 `bestShift` 行"——只要单次滚动量小于底栏高度，追加的整条就是底栏副本（实测 8 次滚动产生 380px 重复底栏）。同一原因还会抬高匹配代价，导致大滚动时直接 `unmatched`。

## 三、咔嚓现状实测

### 3.1 拼接耗时构成（同一份代码抽出来跑基准）

| 场景 | 单次 append p50 | 其中：图像→缓冲转换 | 位移搜索 | **重画整图** |
|---|---|---|---|---|
| 1600×1200，200 次慢速滚动 | 9.2 ms（p95 12.7） | 108 ms / 20% | 234 ms / 35% | **333 ms / 49%** |
| 2560×1600，120 次滚动 | 19.5 ms（p95 30.3） | 469 ms / 20% | 660 ms / 29% | **1182 ms / 51%** |

- **重画整图是最大开销，且随长图高度线性增长**（每次 append 都新建 `image.height + bestShift` 的 context 并把整张旧图重绘一遍，[ScrollingStitcher.swift](../Sources/Kacha/ScrollingStitcher.swift) 第 74–87 行）→ 累计是 O(n²)。
- **峰值内存 405 MB**（`/usr/bin/time -l` 实测，23700×1600 长图）：单张位图 152 MB，而 append 瞬间同时存在"旧图 + 新 context + 新图"，约 2–3 倍。代码里的 `maxBytes = 160_000_000` 只约束**结果图**，不约束瞬时峰值。
- 以上全部发生在 **MainActor 上**（[ScrollingCaptureSession.swift](../Sources/Kacha/ScrollingCaptureSession.swift) `receive()` 同步调 `stitcher.append`），每 0.25 s 一次 10–30 ms 的主线程停顿，直接和预览渲染抢主线程。

### 3.2 鲁棒性对拍：现有 MAD 搜索 vs ScrollSnap 的 Vision 路线

同一份合成内容、同一次滚动序列（40/120/300/500px 各两轮）：

| 场景 | 咔嚓 MAD（现有） | Vision 全帧 | Vision 5 带共识（ScrollSnap） |
|---|---|---|---|
| A 无固定元素 | **8/8** | 8/8 | 8/8 |
| B 顶部固定栏 60px | **8/8** | 3/8（120/300/500 返回 0） | 6/8 |
| C 顶 60 + 底 80 固定 | 2/8，之后**全部 unmatched** | 0/8 | 0/8（拿不到 4/5 共识） |
| D 动画块 + 抗锯齿抖动 | 0/8 | 0/8 | 3/8 |
| E 周期重复内容（表格/代码） | 位移**每帧都错**（少算 96/288/480px） | 0/8 | 0/8 |
| F 聊天类：底部 120px 输入栏、小步滚动 | 位移 8/8，但**每次都把底栏整条贴进长图**（累计 380px 重复） | 0/8 | 0/8 |

> 说明：合成内容无法代表真实网页的全部形态（本生成器纹理较丰富，白底文字页会更难）。**具体命中率不必当作绝对结论，但失配的机制是确定的**，且每条都能在源码里对上。

### 3.3 根因（对着源码逐条）

| # | 问题 | 位置 |
|---|---|---|
| 1 | **没有底部固定区概念**：只检测顶部 frozen header；追加永远取"新帧最底部 `bestShift` 行"，滚动量 < 底栏高度 ⇒ 追加的就是底栏副本 | `ScrollingStitcher.swift:31-39, 82` |
| 2 | 底栏同时污染代价函数：底栏在重叠区与内容比对必然不一致，把**全体均值**抬过硬阈值 8 ⇒ 大滚动时 `unmatched`（C 场景 2/8 后就全丢） | `ScrollingStitcher.swift:41-58, 72` |
| 3 | 代价聚合太脆：全体均值 + 绝对阈值 8，没有分块共识、没有"最优 vs 次优领先度"判据 ⇒ 周期内容里每帧都挑到一个错误的极小值（E 场景） | `ScrollingStitcher.swift:60-72` |
| 4 | 无位移先验：全范围 1px 暴力扫（`4...min(3h/4, …)`），惯性滚动/大跳变没有预测，也没有多尺度加速 | `ScrollingStitcher.swift:61-71` |
| 5 | 每次 append 重画整图 + 每帧两次全图 RGBA 转换，全在主线程 | `ScrollingStitcher.swift:74-87, 93-105`；`ScrollingCaptureSession.swift:83-109` |
| 6 | **采集分辨率**：`configuration.width = display.width`，而 Apple 文档明确 `SCDisplay.width` 是 **points**（"The width of the display in points."），`SCStreamConfiguration.width` 是输出像素数 ⇒ Retina 屏上长截图很可能只有普通截图**一半的线性分辨率**（⚠️需真机确认：打印 `frame.width` / `selection.width` / `screen.backingScaleFactor`，比值 1.0 即 1x） | `ScrollingCaptureSession.swift:52-53` |
| 7 | 没有帧静止门控：0.25 s 定时抓帧，抓到滚动动画中间帧就整帧丢弃（没有"等静止再量"） | `ScrollingCaptureSession.swift:84` |
| 8 | 没有结束/失败语义：到底检测、连续失配上限、"部分成功"状态都没有，只有一句"请缓慢滚动" | `ScrollingCaptureSession.swift:103-106` |

## 四、优化清单（按性价比排序）

### P0 — 不换架构就能拿到大部分收益（✅ 2026-09-30 已全部落地，实测见 §七）

1. **把固定元素泛化成 top / bottom / right 三元组，并且从"追加的内容"里剔除**（不是只从"匹配代价"里剔除）
   - 追加条带改为取**内容区**：源区间 `y ∈ [height - bottomFixed - bestShift, height - bottomFixed)`，而不是 `[height - bestShift, height)`。
   - 参考：macshot `ScrollFrameAnalyzer.frozenTopRows()` / `scrollbarWidth()`（逐行/逐列平均 SAD，阈值 8，滚动条扫描右侧 `min(50, width/8)` 列、行区间 20%–80%）；ShareX `AutoIgnoreBottomEdge`；deepin `getTopFixedHigh/getBottomFixedHigh`。
   - 关键细节（macshot 源码注释原文）：**必须走每张图自己的 `bytesPerRow`**，用 `width*4` 推算 stride 在 window server 行对齐补齐时会逐行累积错位。咔嚓的 `pixels(of:)` 用自建 context 规避了这个坑，但如果改成直接读 `CGImage.dataProvider` 就要注意。
   - 验收：聊天窗口（底部有输入栏）滚 10 次，长图里输入栏只出现在最后一屏，且只出现一次。

2. **代价函数改成"鲁棒聚合 + 拒绝歧义"**
   - 均值 → **分块共识 + 分位数/截尾均值**（跳过最差的若干行，天然忽略动画区与固定区）。
   - 加**次优领先度**判据：冠军必须比"非相邻"的次优好出余量，否则**丢弃该帧**而不是猜（android-scroll-capture 的 `UNIQUENESS_MARGIN`；白云算法的 `lead = score(second) - score(best)`）。
   - 打分函数建议换成**带 mask 的 ZNCC**（即 OpenCV `TM_CCOEFF_NORMED`，公式 `R = Σ(T'·I') / √(ΣT'²·ΣI'²)`，减窗口均值、值域 [-1,1]）：它**支持逐像素 mask**，可以把固定顶栏、右侧滚动条列、动画区直接置 0 权重——按列/行采样的 MAD 做不到这一点。Swift 不必引 OpenCV，用 vDSP/SIMD 或积分图（summed-area table）自己算即可，积分图能把每个候选窗口的 NCC 降到 **O(1)**。
   - 想要**亚像素位移 + 现成置信度**，可用相位相关（`cv::phaseCorrelate` 思路，自己用 Accelerate/vDSP 做 FFT）：5×5 加权质心给亚像素，返回的 `response` 归一化到 1，**单峰=1、多峰更小**，天然是"重复纹理/歧义匹配"的判别器；`disambiguate` 类机制专治周期内容。注意固定带会在互功率谱里贡献恒定伪峰，**必须先剔除固定带**。
   - 模板带/参考带要**选有纹理的**（android-scroll-capture `MIN_TEMPLATE_ACTIVITY`），纯色区到处都能匹配，会得到垃圾位移。
   - 别只用"每行均值"当签名：Seamly（无 LICENSE，仅思路）记录了"真实滚动与其镜像塌缩成平局 ⇒ 符号搞反、连修三轮"的真实 bug，要比较**整条横向签名**。
   - 验收：E 场景（周期内容）不再产生错误位移（宁可不追加，也不要追加错）。

3. **匹配挪到后台队列 + 增量合成（不改行为，只改性能）**
   - 匹配放 `DispatchQueue(label:qos:.userInitiated)` 或 actor（ScrollSnap 用 `stitchingQueue`，macshot 用 `captureQueue`）。
   - 合成改成**只画新增行**、保留一个可增长的缓冲/分块集合，结束时再产出最终 `CGImage`。参考 AOSP 的 `ImageTileSet` + `TiledImageDrawable`（分块存、按需绘制）。
   - 验收：2560×1600 场景下 120 次滚动的拼接 CPU 从 2.3 s 降到 0.5 s 以内，主线程无 10 ms 以上停顿，峰值内存不再随长图翻倍。

4. **修采集分辨率 + 只抓选区**
   - `configuration.width/height = display.width/height * backingScale`（或直接设 `captureResolution = .best` 并实测），并且用 `SCStreamConfiguration.sourceRect` 把采集范围限制到选区（顺带省下 90% 以上带宽和 `CIContext` 转换开销）。
   - 验收：长截图与普通截图的文字锐度一致（同屏同字号对比）。

### P1 — 让"手动滚动"真正可靠

5. **等静止再测量**（macshot 的核心可靠性来源）：连续两帧 TIFF 字节完全相等才认为画面静止；指数退避 10→80 ms，最多 30 次。手动模式下滚动中按 0.15 s 节流直抓 + 停手后 0.25 s 再做一次 settled capture。
6. **最小位移 + 累积**：位移小于 `height/10` 就不更新参考帧，让位移累积（避免抖动被当成滚动）。
7. **接缝容错**：`safeOffset = max(1, offsetPx - 1)`，故意多重叠 1 行让新帧覆盖接缝，掩盖亚像素渲染差异（macshot 注释明说这是有意为之）。**不要羽化**（多个来源都选择硬切）。
8. **失配/到底语义**：连续 8 次匹配失败 或 连续 6 次零位移才判定结束（xland 注释：曾经用 2 次，用户反馈"明明还能滚"）；对外暴露 `Successful / PartiallySuccessful / Failed`（ShareX）或 `RollingTooFast / ReachBottom / MaxHeight`（deepin）。
9. **位移先验 + 由近及远 + 提前终止（单独这一条就能解决"慢"）**：最近 3–5 条接缝取中位数作为期望位移，在 **±48px 有界**范围内重搜（白云算法）；或从上一次偏移 `p` 出发按 `p, p+1, p-1, p+2, …` 向外扩展、MAD 低于阈值立即早停（wayscrollshot col-sample 明写复杂度 **O(9×height)** 而非 O(width×height)；screenshot-splicing 还给了线性速度预测与丢帧规则："期望 300px、每帧 90px → 丢 2 帧、预测 270px"）。配合列投影/列分组采样，搜索成本可降到与位移范围无关。

### P2 — 体验升级

10. **自动滚动**（macOS 唯一开源完整样本：macshot，GPL-3.0 只读思路）：
    1. `CGWindowListCopyWindowInfo([.optionOnScreenOnly, .excludeDesktopElements])` 在**选区中心**命中测试，取 `layer == 0` 且非自家窗口的 PID 与 windowID；
    2. `NSRunningApplication(pid).activate()`；
    3. **`CGWarpMouseCursorPosition` 把光标移到选区中心**——滚轮事件按光标下窗口路由，这一步不能省；
    4. `CGEvent(scrollWheelEvent2Source: nil, units: .line, wheelCount: 1, wheel1: -N, wheel2: 0, wheel3: 0)?.post(tap: .cghidEventTap)`（负值向下），起手先等 300 ms，按速度档 burst 1–4 个；
    5. 每轮：发滚轮 → 等"连续两帧 TIFF 相等" → 测量 → 合并；
    6. 退出：连续 8 次失配 / 连续 6 次零位移 / 高度上限（macshot 默认 30000px）。
    - ⚠️ 需实测：`cghidEventTap` + `NSEvent.addGlobalMonitorForEvents(.scrollWheel)` 通常还需要**辅助功能 / 输入监控**授权，而 macshot 的 README 只声明了屏幕录制权限，源码里也没看到 `AXIsProcessTrusted` 检查。
    - 为什么这条路值得做：**AOSP 的长截图压根不做图像匹配**。它要求被截应用实现 `ScrollCaptureCallback`，由 helper 直接返回结构化位移（`ScrollResult.scrollDelta`，例如 `view.getScrollY() - mStartScrollY`），框架只按 `availableArea` 裁图并按 tile 拼接。把"猜未知位移"变成"已知位移"，是最根本的可靠性提升。
    - macOS 上没有应用配合，所以按这个顺序退化：**(a) 自己合成滚动事件并累计 delta**（macshot 路线，下面 1–6 步）→ **(b) 用 Accessibility 读滚动条数值**（`kAXValueAttribute`，对标准 NSScrollView 应用有效，可当独立位移来源）→ **(c) 像素匹配退居兜底/校验**。
11. **反向滚动 / 向上补内容**：ScrollSnap 的做法是"反向位移必须连续出现两次"才裁剪底部，避免抖动误裁。
12. **预览性能**：长图每次 revision 都让 SwiftUI 重绘整张 `CGImage`（[ScrollingCaptureSession.swift](../Sources/Kacha/ScrollingCaptureSession.swift) `ScrollingPreviewView`）。长图过万像素后建议改成"只显示底部固定高度窗口"或对预览单独降采样缓存。

## 五、明确"不要做"的事

- 不要照抄 ScrollSnap 的 **Vision 全帧配准**作为主路径：实测有固定 chrome 时会返回 0 位移；ScrollSnap 自己是靠"先做 5 条带共识、失败才回退全帧且要求 confidence ≥ 0.9"兜着，而它的条带布局在"顶栏+底栏"同时存在时恰好凑不齐 4/5。
- 如果要用 Vision：**必须先裁掉固定顶栏和右侧滚动条再注册**（macshot 就是这么做的，`cropY = min(headerHeight, height/5)`、`cropW = width - rightMarginPx`），并且校验返回位移的有限性与范围，否则 `Int(round(NaN))` 会崩。
- 不要再去找 AOSP 里的 "TileMatcher"，也不要引用"32 采样列 / 48 采样行 / MAD / 阈值 8"这类"抄自 AOSP"的说法：**AOSP main 分支的 `screenshot/scroll/` 目录里没有 TileMatcher**（本次已核实目录清单，12/13 分支核对同样未找到），AOSP 根本不走图像匹配。这类常量在 Linux 侧的开源工具（wayscrollshot / screenshot-splicing）里有出处，要用就引那边。
- `mrcoles/full-page-screen-capture` 仓库与 raw 路径均已 404，不要作为参考链接。
- 不要用累积 SSD 做代价：y=0 时比较行数多、容错空间大，在小滚动 + 平滑区域反而得分更低 ⇒ 误判"没滚动"（xland `CapLong.cpp` 注释明确记录了这个坑；咔嚓用的均值不受影响）。
- 匹配误差阈值（现在是硬编码 8）不要当成通用常数：博客园那份工程笔记的建议是按内容类型分别标定（PNG / JPEG / 视频截帧各不相同）。

## 七、已落地的改动与实测（2026-09-30）

### 7.1 改了什么

| 文件 | 变化 |
|---|---|
| `Sources/Kacha/FramePixels.swift`（新增） | 逐帧像素访问：只接受 8bpc/32bpp RGB，通道偏移由 `alphaInfo` + `byteOrder` 推出（BGRA 与 RGBA 共用一套代码）；地址一律走图像自身的 `bytesPerRow` |
| `Sources/Kacha/RowCanvas.swift`（新增） | 增量长图画布：按上限一次性 malloc、追加只 memcpy 新增行、指针恒定 ⇒ `makeImage()` 零拷贝、`makePreview()` 降采样预览 |
| `Sources/Kacha/ScrollingStitcher.swift`（重写） | 固定 top/bottom/right 三元组检测；只在**内容区**匹配与取条带；行签名 + 纹理加权 + 截尾均值打分；次优领先度判歧义；预测窗口加速；失配不推进参考帧 |
| `Sources/Kacha/ScrollingCaptureSession.swift`（改造） | 拼接移到 actor（后台执行）；采集分辨率改为 `display.points × backingScaleFactor`；回调里按实际缓冲区尺寸直接裁 `CVPixelBuffer`；预览改用降采样图；帧率 8→15fps，最短处理间隔 60ms |
| `Tests/KachaTests/ScrollingBandTests.swift`（新增 8 条） | 底栏不重复（与理想长图逐像素对拍）、大滚动不再失配、底栏图案不出现、固定栏内稀疏动画（光标闪烁）、滚动条列、歧义拒绝、周期内容判"没动"、小位移累积 |
| `Tests/KachaTests/RowCanvasTests.swift`（新增 6 条） | 增量追加、回退覆盖、容量上限、截断、零拷贝快照后再追加、预览降采样 |

行为变化（对应 §四 P0）：
1. **固定底栏不再被贴进长图**：追加条带取自 `[contentBottom - shift - 2, contentBottom)`；首帧若含底栏，先 `truncate` 回内容区边界再追加。
2. **打分不再被固定栏/动画顶穿**：16 块行签名、按行纹理加权、丢掉最差 25% 权重后用**截尾加权均值**；最优位移还要比"非相邻次优"好出 `uniquenessMargin`，否则判 `.unmatched` 而不是猜。
   固定区判定的"静止行"除平均差之外还看**变化像素占比**（≤2%）：只看平均差时，固定栏里一个闪烁的输入框光标就足以让"从边界连续数静止行"提前中断，底栏被判小、那一截又被追加进长图。
3. **小位移会累积**：失配时保留上一次成功接上的参考帧；`score(0)` 足够小才报 `.unchanged`。
4. **性能**：不再每次重画整图；匹配挪出主线程；预览只画降采样图。
5. **封盘语义**：`finishImage()` 会把 actor 置为 sealed，之后到达的帧一律丢弃 —— 否则主线程在编码 PNG 时会与 actor 写同一块画布缓冲区并发（`makeImage()` 是零拷贝包装）。
6. **采集分辨率**用 `SCContentFilter.pointPixelScale` × `contentRect`，而不是 `backingScaleFactor`：显示器跑缩放分辨率时两者不同（例：1920pt 逻辑宽度在 2880px 面板上是 1.5）。

### 7.5 独立复核后的修正（同日）

复核方用**独立 SPM 包**（源码逐字节拷贝，与我们无共享代码）复现了 9 类问题，已逐条修复：

| 复核发现 | 处理 |
|---|---|
| ① 固定区检测有 `height/4` 硬上限：底栏 >25% 视口时边界切进底栏内部，之后每次追加取到的都是底栏像素 | 去掉上限，改为"至少留 32 行可动内容"+ 两侧合计超预算时压回 |
| ② 底栏像素帧间有变化（宽进度条 / 毛玻璃 / 跑马灯）时检测不到 | 静止游程允许 ≤ `max(8, 高/50)` 行的间隙（进度条、缩略图这类大面积动画） |
| ③ 大片纯色（≥2/3 视口）+ 保留参考帧 ⇒ 永久 unmatched、长图丢后半页 | ①"画面没动"不再要求纹理配额；②相邻帧能对齐就**立刻重锚**（`didRealign` 提示用户）；③6 次失配兜底重锚 |
| ④ 底栏中途出现 ⇒ 多出的底栏被当内容追加 | 合成边界随固定栏变大同步下移，并把已画进画布的固定栏行截掉 |
| ⑤ 帧尺寸变化 ⇒ 永久静默失配 | 新增 `.sizeChanged` 语义 + UI 提示；尺寸恢复后可继续拼 |
| ⑥ 位移 > 7/8 内容高（Page Down）不可匹配 | 最小重叠从 1/8 放宽到 `max(24, 内容高/12)`（约 8%） |
| ⑦ 宽度 < 4 时右缘扫描读到负列号 | 列索引 clamp（原先靠 UI 最小选区 4pt 侥幸不可达） |
| ⑧ `RowCanvas` 语义：空区间返回 false、`makeImage()` 不是快照 | 空区间改为合法 no-op；`makeImage()` 改为**只拷贝实际行的快照**（导出图不再被后续 append 改写，也不再钉住整块容量内存） |
| ⑨ 真实位移 < `minimumShift` 时可能接受周期别名 | 1…`minimumShift`-1 也纳入打分；最优低于最小位移则保留参考帧等它累积 |

并发/生命周期复核（另一路，同样独立复现）的关键结论：
- **交付后的零拷贝导出图会被 actor 继续写入**——真实数据竞争（用 actor 优先级越过复现）；我们的 `isSealed`/`finishImage()` 修复被其复验为有效（现在再加上快照语义，双保险）；
- provider retain/release 配对正确，**不存在 use-after-free**；
- 不存在任务堆积（单帧 0.4–0.7ms vs 66ms 帧间隔）；
- 唯一保留的输入假设是 SCK 帧格式 → 已加 `CVPixelBufferGetPixelFormatType` 校验 + CoreImage 回退 + alpha 改 `noneSkipFirst`。
